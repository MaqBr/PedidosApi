Por que Docker + ACR?
  • 📦Artefato imutável — a mesma imagem que passa nos testes vai para produção
  • 🔁Consistência — mesmo runtime do dev ao stable, sem surpresas de ambiente
  • 🏷️Rastreabilidade — cada imagem tem a tag da versão exata (ex: 1.0.0-rc.1)
  • ⚙️Configuração como código — ASPNETCORE_ENVIRONMENT definido pelo pipeline
  • 💻Portabilidade local — docker compose up roda o mesmo container
  • 🔒Segurança — usuário não-root, imagem mínima, sem SDK no runtime

Separação de responsabilidades
  • 🧪Host do agente
    Testes, cobertura, SonarCloud — precisa do SDK para análise estática
  • 🐳Docker build stage
    dotnet publish com versão baked via --build-arg
  • ☁️ACR
    Registry privado, integrado ao Azure por Managed Identity
  • 🚀Web App Container
    Pull da imagem exata + ASPNETCORE_ENVIRONMENT via pipeline
Stage CI — 9 passos
  • 1Instalar .NET SDK 10.x
  • 2Calcular versão SemVer + tag de ambiente (isOutput=true)
  • 3Restaurar pacotes NuGet
  • 4SonarCloud Prepare
  • 5dotnet build (para testes)
  • 6dotnet test + cobertura XPlat
  • 7SonarCloud Analyze
  • 8SonarCloud Publish + Quality Gate
  • 9Docker buildAndPush → ACR
    2 tags • build args de versão
Nota: Os passos 1–8 rodam no agente com o SDK. O passo 9 executa um novo dotnet publish dentro do Docker — por isso o SDK não precisa estar na imagem final.
Dockerfile — Versão via build args
Dockerfile
# Estágio 1: Build
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build

# Injetado pelo pipeline
ARG VERSION=0.0.0
ARG ASSEMBLY_VERSION=0.0.0

COPY PedidosApi.csproj ./
RUN dotnet restore

COPY . .
RUN dotnet publish \
  -p:InformationalVersion=${VERSION} \
  -p:AssemblyVersion=${ASSEMBLY_VERSION}

# Estágio 2: Runtime (sem SDK)
FROM mcr.microsoft.com/dotnet/aspnet:10.0
USER 1000
COPY --from=build /app/publish .
ENTRYPOINT ["dotnet", "PedidosApi.dll"]
Pipeline (Docker@2)
- task: Docker@2
  inputs:
    command: buildAndPush
    containerRegistry: sc-acr-pedidosapi
    repository: pedidosapi
    tags: |
      $(versao.appVersion)
      $(versao.envTag)
    arguments: >
      --build-arg VERSION=$(versao.appVersion)
      --build-arg ASSEMBLY_VERSION=$(assemblyVersion)
Resultado: GET /info retorna a versão exata da tag git baked na imagem.
Estratégia de tags no ACR

Cada build gera duas tags — a versão imutável e a referência do ambiente.

TriggerTag de versãoTag de ambienteDeploy automático
branch main 0.0.0-20260507.1 alpha ✅ Alpha
tag v1.0.0-alpha.1 1.0.0-alpha.1 alpha ✅ Alpha
tag v1.0.0-beta.1 1.0.0-beta.1 beta ✅ Beta
tag v1.0.0-rc.1 1.0.0-rc.1 rc ⏳ RC (aprovação)
tag v1.0.0 1.0.0 stable ⏳ Stable (dupla aprovação)
Deploy sempre usa a tag de versão (imutável) — nunca a tag de ambiente, que pode ser sobrescrita por um build posterior.

Cada stage executa:
- task: AzureWebAppContainer@1
  inputs:
    azureSubscription: sc-azure-pedidosapi
    appName: $(APP_NAME_ALPHA)
    containers:
      $(ACR_LOGIN_SERVER)/pedidosapi:$(appVersion)
    appSettings: -ASPNETCORE_ENVIRONMENT Alpha
